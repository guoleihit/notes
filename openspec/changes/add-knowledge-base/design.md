## Context

- 当前仓库为空（仅含 OpenSpec 脚手架），无既有代码。
- 目标用户是开发者本人；笔记为学习笔记，以中文为主。
- 动机见 proposal.md - Why。核心约束：数据所有权（本地纯文本、可迁移、防丢失）；检索用关键词而非 embedding；生成层复用现有 OpenCode Go 订阅（GLM 聊天模型）。

## Goals / Non-Goals

**Goals:**
- 笔记永远以本地纯文本 + git 承载，可迁移、防丢失。
- 用 grep 关键词检索替代 embedding 语义检索，零额外 API 成本、免维护索引。
- 问答复用 OpenCode Go 的 GLM 聊天模型，按需调用、零额外订阅。
- 通过 `kb lint` 按需整理知识库，发现关联与问题，增量处理并记录档案。

**Non-Goals:**
- 不引入 embedding 模型、向量索引、向量数据库。
- 不引入知识图谱（实体/关系抽取成本高、噪声大；个人量级用双链 + lint 建议即可）。
- 不自建笔记编辑器（由 Obsidian 承载）。
- 不做多用户、协作、云同步、移动端。

## Decisions

1. **存储 = 纯文本 Markdown + git，按目录分类组织**（而非数据库或专有格式）
   - 理由：防丢失、可迁移；git 提供版本化；目录分类为关键词检索提供结构支撑。
   - 备选：SQLite 存内容、Notion 等专有格式 → 放弃（数据锁定、迁移风险）。

2. **编辑器 = 外部工具（Obsidian）**（而非自建编辑器）
   - 理由：编辑体验是成熟问题，不自造轮子；内容层与工具解耦。

3. **检索 = grep 关键词匹配**（而非 embedding 语义检索）
   - 理由：零成本、可解释、实时、免维护索引；配合良好目录分类与命名，个人量级足够。
   - 备选：embedding + 向量索引 → 放弃（额外 API 成本、本地高配置、同义词收益有限）。若未来漏召回成为真实痛点，再引入 embedding（升级路径开放）。

4. **LLM = OpenCode Go 的 GLM-5.2**（chat/completions，OpenAI 兼容）
   - 理由：复用用户已有订阅，零额外成本；glm-5.2 配额（$60）高于 glm-5.3（$15），问答足够。
   - 端点：`https://opencode.ai/zen/go/v1`，模型 `glm-5.2`，经 OpenAI 兼容 SDK 调用。
   - 备选：智谱开放平台、本地 Ollama → 均需额外 key/配置，作为可替换项。

5. **lint = 关键词共现 + 增量档案**（关联发现）
   - 零成本档：对新/改笔记，用关键词重叠找候选相关笔记，并识别孤立笔记。
   - 档案 `.kb_cache/lint.json`：记录每个文档的内容 hash 与上次 lint 结果，仅对变更文档重新 lint。
   - 可选 `--llm`：让 GLM 精判候选对是否真相关（有成本，档案记录每次处理了哪些文档）。

6. **模型抽象层 = OpenAI 兼容接口**
   - 理由：OpenCode Go、智谱、Ollama 等均兼容该协议，切换只改 base_url 与模型名。

## Risks / Trade-offs

- [关键词检索漏召回（同义词/改写）] → 靠良好目录分类与命名缓解；`kb ask` 可由 LLM 在命中文档基础上补充理解；未来可引入 embedding 兜底。
- [LLM 回答可能编造（无命中时）] → spec 明确要求无候选文档时提示而非编造。
- [lint 的关联判断精度有限（关键词共现）] → 提供 `--llm` 精判档；档案保证不重复花钱。
- [LLM 调用成本随问答频率增长] → 按需调用，Go 订阅已覆盖；问答结果可缓存避免重复。
