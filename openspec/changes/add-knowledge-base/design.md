## Context

- 当前仓库为空（仅含 OpenSpec 脚手架），无既有代码或笔记。
- 目标用户是开发者本人；笔记为学习笔记，以中文为主。
- 动机见 proposal.md - Why。核心约束：数据所有权（本地纯文本、可迁移、防丢失）；AI 语义检索暂用云端 API，未来可能切换本地模型。

## Goals / Non-Goals

**Goals:**
- 笔记永远以本地纯文本 + git 承载，可迁移、防丢失。
- 以语义检索 + 关联推荐替代繁重的分类组织，降低记笔记的组织成本。
- 模型层可插拔，云端 → 本地切换不改变行为。

**Non-Goals:**
- 不自建笔记编辑器（编辑体验由 Obsidian 等现成工具承载）。
- 不做多用户、协作、云同步服务。
- 不做移动端应用。

## Decisions

1. **存储 = 纯文本 Markdown + git**（而非数据库或专有格式）
   - 理由：防丢失、可迁移；git 天然提供版本化，并可复用为变更检测器。
   - 备选：SQLite 存内容、Notion 等专有格式 → 放弃（数据锁定、迁移风险）。

2. **编辑器 = 外部工具（Obsidian）**（而非自建编辑器）
   - 理由：编辑体验是成熟问题，不自造轮子；内容层与工具解耦，笔记文件不绑定任何工具。
   - 备选：自建编辑器 → 延迟到出现真实痛点时再考虑。

3. **变更检测 = git（status/diff）**（而非文件时间戳或全量扫描）
   - 理由：git 是唯一真相，能精确识别新增/修改/删除，且与版本化复用同一套基础设施。
   - 备选：mtime 时间戳（不可靠，易误报漏报）、全量重建（成本随笔记量线性增长）。

4. **向量索引 = 本地文件型向量存储（sqlite-vec / chromadb）**
   - 理由：单用户量级小，无需独立服务；索引作为缓存随笔记仓库一起备份，可随时重建。
   - 备选：独立向量数据库服务（Pinecone/Weaviate 等）→ 对个人场景过度。

5. **模型抽象层 = OpenAI 兼容接口**
   - 理由：主流云端（智谱/硅基流动/OpenAI）与本地（Ollama）大多兼容该协议，切换只需改 base_url 与模型名。
   - 备选：各 SDK 直连 → 切换成本高，未来本地化受阻。

6. **存储层与检索层分离**
   - 检索索引是可替换、可重建的缓存；唯一真相始终是 Markdown 文件，索引损坏可随时从源文件重建。

7. **检索层实现语言 = Python**
   - 理由：AI/RAG 生态最成熟（chromadb、sentence-transformers、OpenAI 兼容 SDK 等），中文 embedding（BGE-M3）与本地模型（Ollama）支持最好。
   - 备选：Node/TypeScript → 中文 embedding 与本地模型库生态弱于 Python。

## Risks / Trade-offs

- [云端 API 成本随笔记量增长] → 增量索引 + 缓存已索引状态，避免重复计算；将来切本地模型。
- [向量检索存在漏召回（语义相近但未返回）] → 后续可扩展为混合检索（关键词 BM25 + 向量）作为补充。
- [中文语义质量依赖 embedding 模型] → 选用中文强的模型（如 BGE-M3），且模型层可替换以随时升级。
- [造工具挤占学习时间] → 阶段 0 先开始记笔记，检索层按真实痛点增量叠加。
