# KV Cache（键值缓存）

> 整理日期：2026-11-08
> 主题：LLM 推理服务层最核心的工程优化之一。

---

## 一、一句话

**KV Cache 是推理时把「已处理过的 token 的 Key/Value 向量」缓存起来，生成下一个 token 时直接复用，避免重复计算。**

它不改变模型精度，只加速推理、并决定显存能撑多长的上下文。

---

## 二、为什么需要它

Transformer 的注意力里，每个 token 会算三个向量：**Q（查询）、K（键）、V（值）**。输出 = 用 Q 去和所有 K 匹配出权重，再对所有 V 加权求和。

大模型是**自回归生成**：一个 token 一个 token 往后吐。生成第 `t` 个 token 时，它要「看到」前面所有 token 的 K 和 V。

- **没有缓存**：每生成一个新 token，都要把所有历史 token 的 K、V 重新算一遍 → 每步 `O(n)` 次计算，整体 `O(n²)`~`O(n³)`，越长越慢。
- **有缓存**：历史 token 的 K、V 已经算过且**不会变**（对当前请求而言），存下来；新 token 只算自己的 Q、K、V，然后拿 Q 去查缓存的 K、V → 每步从 `O(n)` 降到只算 1 个 token。

> 注意：K、V 对「之前的位置」是固定的，Q 才是每个新 token 自己的。这就是为什么只缓存 K、V，不缓存 Q。

---

## 三、代价：吃显存

KV Cache 的大小大致是：

```
2（K 和 V） × 层数 × 头数 × 序列长度 × 每头维度 × 数据类型字节数 × batch
```

关键结论：

- **随序列长度、batch、模型规模线性增长**。这是长上下文「又贵又慢」、并发上不去的根本原因之一。
- 它是**每个请求独立的运行时状态**，和固定的模型权重是两回事。

---

## 四、相关工程优化

| 技术 | 作用 |
|---|---|
| **PagedAttention**（vLLM） | 像虚拟内存分页一样管理 KV Cache，按块分配，减少显存碎片、提升吞吐 |
| **Prefix Caching** | 多个请求共享相同前缀（system prompt、few-shot）时复用同一份 KV，省重复计算 |
| **Continuous Batching** | 动态把新请求塞进正在跑的 batch，配合 KV Cache 提高 GPU 利用率 |
| **KV Cache 量化** | 把缓存从 FP16 压到 INT8/FP8，省显存（略损精度） |
| **GQA / MQA** | 让多个 Query 头共享少量 K/V 头，从模型结构上直接减小 KV Cache |

---

## 五、和「上下文窗口」的关系

KV Cache 就是「模型在一次生成中记住了前面内容」的物理载体。

- 上下文越长 → KV Cache 越大 → 显存压力越大。
- 这也是为什么长上下文通常要额外收费、并发数要降低。

---

## 六、结论

> **KV Cache 用显存换时间：把历史 token 的 K/V 存下来复用，让自回归生成不必每步重算全序列。它是推理加速的基石，也是长上下文成本的主要来源。**
