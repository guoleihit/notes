## 一、明确错题

### 错题 1：CoT 提示设计推荐做法

**题目：**  
在使用思维链（CoT）提示设计 LLM 提示词时，以下哪些做法是推荐或必要的？

**选项：**

- A. 使用简洁和一致性的提示
    
- B. 提供大量的示例样本
    
- C. 结合零样本提示技巧
    
- D. 保持问题的深度和广度平衡
    
- E. 忽略模型的归纳能力
    

**我的初始答案：** A、C  
**正确答案：** A、B、C、D

**错误分析：**

- **漏选 B**：最初认为“大量示例样本”不推荐，担心成本高、干扰模型。实际上，CoT 推荐提供 **3~5 个高质量、多样化的示例**，这可以视为“适量的大量”。只要质量高、覆盖边缘情况，就是有效做法。
    
- **漏选 D**：最初认为“深度和广度平衡”不是 CoT 核心要求。实际上，CoT 需要根据任务复杂度校准推理步骤的粒度和数量，避免过深或过浅，这是设计高质量 CoT 的重要原则。
    

**知识点总结：**

- CoT 提示应简洁、格式一致。
    
- 少样本 CoT 推荐提供 **少量高质量示例**，而非越多越好。
    
- 零样本 CoT（如“让我们一步一步思考”）可作为低成本补充。
    
- 推理链的深度与广度需与任务复杂度匹配。
    
- 应充分利用模型的归纳能力，而非忽略。

### 错题 2：分隔符的主要目的

**题目：**  
以下选项中属于使用分隔符的主要目的有哪些？

**选项：**

- A. 规范化文档格式
    
- B. 明确提示词各要素之间的界限
    
- C. 使文档看起来更复杂
    
- D. 增加文字数量
    
- E. 随意分割文本
    
- F. 提高模型的运行速度
    

**我的初始答案：** B  
**正确答案：** A、B

**错误分析：**

- **漏选 A**：最初认为“规范化文档格式”只是辅助效果，不是主要目的。实际上，使用分隔符（如 `###`、`"""`、XML 标签、代码块等）可以统一提示词结构，使角色、上下文、任务、输出格式等模块清晰规范，这本身就是主要目的之一。
    
- **B 仍是核心目的**：明确各要素界限，避免模型混淆。
    

**知识点总结：**

- 分隔符的核心作用：
    
    1. **明确提示词各要素的界限**（内容层面）
        
    2. **规范化文档格式**（形式层面）
        
- 常见分隔符：`###`、`"""`、`---`、XML 标签、Markdown 标题、代码块等。
    
- 不应为了复杂、凑字数或随意分割而使用分隔符。

## 二、争议与易错点

### 1. 固定 seed vs 固定 temperature

**题目：**  
希望同一提示词每次尽最大可能返回相同结果，最关键一步是？

**选项：** A. 固定 top_p B. 固定 temperature C. stream=False D. 固定 seed

**正确答案：** B  
**易错点：** 有人选 D（固定 seed），认为固定 seed 可让结果完全一致。

**解析：**

- `temperature=0` 才是确定性生成的关键，模型会选择概率最高的 token，消除采样随机性。
    
- `seed` 只保证随机采样过程可复现，不能消除随机性；且受浮点运算、并行计算、硬件等因素影响，很多 API 不保证 100% 一致。
    
- `top_p` 和 `temperature` 并非“仅控制多样性”，`temperature=0` 直接影响结果一致性。
    
- `stream` 只影响输出模式，不影响内容。
    

**结论：** 最关键一步是 **固定 temperature（通常设为 0）**。

### 2. 角色设定是否属于上下文

**题目：**  
以下哪些选项体现了提示词要素中的“上下文（Context）”？

- A. 用户喜欢历史文化景点，不喜欢游乐场。
    
- B. 请提供不少于三个景点的推荐。
    
- C. 输出格式为 JSON。
    
- D. 请你扮演一位资深旅游博主。
    
- E. 请根据用户提供的行程安排，推荐合适的旅游景点。
    
- F. 用户计划前往北京旅游，时间为一周。
    

**正确答案：** A、F  
**我的答案：** A、F  
**争议点：** 角色设定（D）是否属于上下文？

**解析：**

- **严格按提示词要素分类**：角色设定（Role/Persona）通常单独列为独立要素，不算“上下文（Context）”。
    
- **广义理解**：角色设定也可视为背景信息的一部分，可算作广义上下文。
    
- **考试建议**：若题目明确区分“角色、任务、上下文、输出格式”，则角色设定不选入“上下文”。

### 3. 输出格式 vs 风格

**题目：**  
以下哪些选项属于提示词要素中的“输出格式（OutputFormat）”？

- A. 我希望你以第一人称的口吻写作。
    
- B. 请你总结一下这篇文章的主要内容。
    
- C. 结果需要包含姓名、年龄和地址。
    
- D. 请使用 JSON 格式输出。
    
- E. 假设你是一个资深律师。
    
- F. 请用表格形式展示结果。
    

**正确答案：** C、D、F  
**我的答案：** C、D、F  
**争议点：** 为什么 A 不选？为什么 C 选？

**解析：**

- **输出格式**关注：结果的结构、字段、排版、类型、展示方式。
    
- **风格/语气/人称**关注：用什么语气、从谁的角度说。
    
- A 规定的是第一人称口吻，属于风格，不是输出格式。
    
- C 规定输出必须包含姓名、年龄、地址，属于结构/Schema，是输出格式的一部分。
    
- D 指定 JSON 格式，F 指定表格形式，均属于输出格式。
    

**输出格式可包含：** 结构化格式、字段与 Schema、展示形式、长度与粒度、排版与标记、数据类型规范、顺序与层级、附加约束等。

### 4. max_tokens 可能导致回答不完整

**题目：**  
智能助手回答过于冗长，哪种方法能有效控制回答长度？

- A. 设置最大 token 限制
    
- B. 要求模型“简短回答”
    
- C. 要求模型“用一句话回答”
    
- D. 在提示词中明确要求“回答不超过 50 字”
    

**正确答案：** A  
**易错点：** A 会不会让回答不完整？

**解析：**

- `max_tokens` 是硬限制，设置过小会导致回答被硬性截断，可能不完整。
    
- 它不会自动压缩成完整句子，达到上限立即停止。
    
- 要兼顾长度与完整性，应：
    
    - 将 `max_tokens` 设得比目标长度稍大，留余量；
        
    - 同时用提示词软约束，如“请用不超过 50 字完整回答”；
        
    - 检查 `finish_reason` 是否为 `length`；
        
    - 复杂问题分段生成；
        
    - 可使用 `stop` 参数。
        

**结论：** A 有效但有代价，实践中应作为硬性兜底，配合软性提示。

### 5. 限制用户查询长度

**题目：**  
新员工帮助应用中，哪些建议有助于提升用户体验？

- A. 为每个任务定制详细的系统提示词
    
- B. 限制用户查询长度
    
- C. 引入多轮对话机制
    
- D. 无需提供反馈或修正机制
    
- E. 实现自动检测用户查询类型并调用相应策略
    

**正确答案：** A、C、E  
**易错点：** 为什么不选 B？

**解析：**

- 限制用户查询长度会妨碍用户充分描述问题，尤其新员工不熟悉术语，可能导致信息不足、回答错误。
    
- 长文本问题应靠系统优化解决：分块、摘要、RAG、流式输出、多轮澄清、异步处理等。
    
- 限制长度是以牺牲用户表达为代价迁就系统，不是提升体验。
    
- 更好做法是“软引导”而非“硬限制”，例如提示用户尽量简要并包含关键信息。

### 6. 严格身份验证流程

**题目：**  
智能客服机器人处理复杂法律咨询，应采取哪些措施？

- A. 引入思维链提示技术
    
- B. 实施严格的用户身份验证流程
    
- C. 提供标准的回答模板
    
- D. 集成自然语言理解模块
    

**正确答案：** A、C、D  
**易错点：** 为什么不选 B？

**解析：**

- 严格身份验证会增加用户使用门槛，降低体验。
    
- 它不是处理复杂法律咨询的核心手段。复杂咨询的关键在于准确理解、多步推理、结构化合规回答。
    
- 很多通用法律咨询不需要身份验证。
    
- 身份验证解决的是访问控制和隐私安全，不是体验和复杂咨询问题。
    
- 更合理做法是按需、分级验证：一般咨询不验证，涉及敏感信息或正式操作时再触发。

## 四、今日总结

今天的主要错题集中在 **CoT 提示设计** 和 **分隔符作用** 两个知识点上，暴露出对“推荐做法”的边界判断过于绝对，以及容易忽略形式层面的主要目的。此外，还有多个争议点和易错点值得注意：

1. **CoT 提示**：示例样本要“适量且高质量”，推理链深度广度需平衡。
    
2. **分隔符**：既划清要素界限，也规范化文档格式。
    
3. **确定性生成**：固定 `temperature=0` 比固定 `seed` 更关键。
    
4. **提示词要素分类**：角色设定、风格、输出格式、上下文需严格区分。
    
5. **长度控制**：`max_tokens` 是硬限制，需留余量并配合软提示。
    
6. **用户体验**：不应硬性限制用户输入或强制严格身份验证，应靠系统优化和按需验证。
    

后续复习时，应更注意：

- 区分“核心目的”与“辅助效果”；
    
- 理解“适量、高质量”在提示词工程中的含义；
    
- 严格按提示词要素分类做题，同时留意广义解释；
    
- 在技术方案中兼顾可靠性与用户体验。
