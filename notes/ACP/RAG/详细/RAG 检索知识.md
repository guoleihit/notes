## 1. 为什么向量检索不够？

向量检索把 query 和文档压成 embedding，用余弦相似度找“语义相近”的片段。它擅长同义改写、自然语言泛化、多语言语义匹配，但有几个硬伤：

1. **精确匹配弱**  
    专有名词、产品型号、错误码、函数名、法律条款、版本号、数字、ID 等，向量容易“模糊化”。  
    例如：`ERR_CONNECTION_REFUSED 怎么解决`，BM25 能精确命中错误码，向量可能只召回“网络连接失败”。
    
2. **相似不等于相关**  
    向量可能召回主题相关但没有答案的段落。RAG 要的是“能支撑答案的证据”，不是“聊到同一个话题”。
    
3. **否定、条件、数值比较容易被平滑掉**  
    “不包含酒精”“价格低于 500”“2023 年之后”这类约束，embedding 往往表达不清，需要关键词、元数据或结构化过滤。
    
4. **长尾实体和领域新词表示差**  
    新版本、内部术语、小众实体在预训练 embedding 中可能没学好，向量召回不稳定。
    
5. **多跳、比较、聚合问题单查询不够**  
    “A 和 B 有什么区别”“根据 X 和 Y 推断 Z”，一次向量检索很难覆盖所有证据。
    
6. **可解释性和可控性弱**  
    BM25 能看出命中了哪些词，向量分数很难解释；企业场景需要权限、时间、来源过滤，也常靠元数据和结构化检索。
    

所以主流 RAG 检索不是“向量 vs 其他”，而是：**多路召回 + 融合 + 重排 + 查询改写**。

## 2. 其它检索方案

### 2.1 BM25 / 稀疏检索

BM25 是经典词项匹配算法，基于倒排索引，考虑词频、逆文档频率和文档长度归一化。它不依赖神经网络，速度快、可解释、对精确词强。

**适合：**

- 专名、ID、代码、错误码、数字、法律条款；
    
- 用户 query 很短且关键词明确；
    
- 领域新词、OOV 词；
    
- 需要过滤和布尔逻辑的场景。
    

**缺点：**

- 不懂同义词和语义泛化；
    
- query 和文档用词不一致时召回差；
    
- 对自然语言长问句不如向量。
    

在 RAG 里，BM25 通常作为与 dense 向量并行的第二路召回。现代实现也常用学习稀疏向量，如 SPLADE、uniCOIL、Elastic ELSER，兼顾词项精确和语义扩展。

---

### 2.2 混合检索

混合检索 = dense 向量检索 + sparse/BM25 检索，并行召回后融合。

典型流程：

1. query 分别走向量检索和 BM25；
    
2. 各取 top 50～200；
    
3. 按 doc/chunk id 去重；
    
4. 融合排序；
    
5. 送入 rerank。
    

融合方式：

- **加权求和**：需要归一化不同分数，调权重麻烦；
    
- **RRF**：按排名融合，简单鲁棒；
    
- **学习排序**：用标注数据训练融合模型。
    

混合检索是当前通用 RAG 最稳的默认方案：向量补语义，BM25 补精确。

---

### 2.3 RRF：倒数排名融合

RRF 不直接比较分数，只看排名：

RRF(d)=∑i1k+ranki(d)RRF(d)=i∑​k+ranki​(d)1​

其中 ranki(d)ranki​(d) 是文档 d 在第 i 路召回中的排名，k 常取 60。

**优点：**

- 不需要归一化不同检索器的分数；
    
- 对某一路分数尺度不敏感；
    
- 多路召回融合简单有效；
    
- 适合向量、BM25、多查询、HyDE 等多路结果合并。
    

**缺点：**

- 丢失分数强弱信息；
    
- 如果某一路质量很差，也会贡献排名；
    
- 可以配合权重，如 wi/(k+rank)wi​/(k+rank)。
    

---

### 2.4 Rerank：精排

两阶段检索：

- **召回阶段**：向量、BM25、混合检索，追求高召回，top 50～200；
    
- **重排阶段**：Cross-Encoder 或 LLM 对 query-doc 对逐条打分，追求高精度，输出 top 5～10。
    

Cross-Encoder 把 query 和文档拼在一起输入模型，能建模细粒度交互，比双塔向量准得多。常见模型：BGE-reranker、Cohere Rerank、Jina Reranker，也可以用 LLM 做 listwise 重排。

**注意：**

- Rerank 很慢，不能对全库跑；
    
- 它不能替代召回，只能优化已召回集合；
    
- 适合解决“向量和 BM25 都召回了，但排序不对”的问题。
    

---

### 2.5 查询改写

查询改写发生在检索前，目标是提升召回。常见方法：

- **Multi-Query**：让 LLM 生成 3～5 个查询变体，分别检索，RRF 融合；
    
- **HyDE**：先生成假设答案，再用假设答案的 embedding 去检索，适合短 query；
    
- **Query Expansion**：加同义词、缩写、领域词；
    
- **Query Decomposition**：把多跳/比较问题拆成子问题；
    
- **Step-back Prompting**：先问更抽象的背景问题，再检索细节；
    
- **意图与过滤抽取**：抽取时间、作者、版本、类别、权限，用于元数据过滤。
    

风险是 query drift：改写后偏离原意。工程上通常保留原 query，一起检索并融合。

---

### 2.6 其他补充方案

- **元数据过滤**：时间、来源、权限、版本、标签，先过滤再检索；
    
- **结构化检索 / Text2SQL**：表格、指标、数据库问题；
    
- **知识图谱 / GraphRAG**：多跳关系、实体链接、社区摘要；
    
- **多向量检索 ColBERT**：token 级 late interaction，兼顾语义和词项；
    
- **父子块 / 句子窗口**：小块检索，大块生成；
    
- **上下文检索**：给 chunk 生成上下文再嵌入；
    
- **路由检索**：按 query 类型选择向量、BM25、SQL、图谱或 API。

## 3. 典型 RAG 检索流水线

text

用户 Query
  -> 查询理解/改写/路由
  -> 并行召回：
       向量检索 top50
       BM25/稀疏检索 top50
       元数据/结构化/图谱检索
  -> RRF 或加权融合
  -> 去重、多样性处理
  -> Rerank top20 -> top5
  -> 上下文组装
  -> LLM 生成 + 引用

**选型建议：**

- 通用文本 RAG：**dense + BM25 + RRF + rerank**；
    
- 代码、日志、法律、医疗：提高 BM25/精确匹配权重；
    
- 多跳、综述：查询分解 + GraphRAG + 迭代检索；
    
- 表格/指标：Text2SQL + 向量混合；
    
- 多语言：多语言 embedding + BM25/稀疏检索。
    

评估时不要只看向量相似度，要看 **Recall@k、MRR、nDCG、答案正确率、引用准确率、延迟**。

## 4. 检索评估指标：Recall@k、MRR、nDCG

这三个都是**检索排序质量评估指标**，但关注点不同：

- **Recall@k**：前 k 个结果里，找回了多少“所有相关文档”。关注“找全没”。
    
- **MRR**：第一个相关结果排得有多靠前。关注“第一个命中位置”。
    
- **nDCG**：整体排序质量，考虑每个结果的相关性等级和位置。关注“排得好不好”。
    

---

### 4.1 Recall@k：召回率

**定义**  
在前 k 个检索结果中，命中的相关文档数，占全部相关文档数的比例。

**公式**

Recall@k=∣前k个结果∩所有相关文档∣∣所有相关文档∣Recall@k=∣所有相关文档∣∣前k个结果∩所有相关文档∣​

**直觉**  
一个 query 真正相关的文档有 5 个，你取 top 10，命中了 4 个：

Recall@10=4/5=0.8Recall@10=4/5=0.8

意思是：相关证据找回了 80%，还有 20% 没找到。

**在 RAG 中**  
RAG 往往需要多个证据 chunk 才能回答。如果 Recall@k 低，说明**该找的资料没进上下文**，后面 rerank 和 LLM 再强也救不回来。

常用：

- 召回阶段看 `Recall@20`、`Recall@50`、`Recall@100`；
    
- 多跳问答、多文档问答尤其重要。
    

**注意**  
Recall@k 不关心相关文档排在第 1 还是第 50，只要在前 k 里就算命中。所以它高，不代表排序好。

---

### 4.2 MRR：平均倒数排名

**定义**  
对每个 query，找到**第一个相关结果**的位置 rank，取倒数 1/rank1/rank，再对所有 query 求平均。

**公式**

MRR=1∣Q∣∑q=1∣Q∣1rankqMRR=∣Q∣1​q=1∑∣Q∣​rankq​1​

其中 rankqrankq​ 是第 q 个 query 的第一个相关结果排名。如果前 k 个里没有相关结果，则倒数排名记 0。

**直觉**

- 第一个相关结果排第 1：得分 1/1=11/1=1；
    
- 排第 2：得分 1/2=0.51/2=0.5；
    
- 排第 5：得分 1/5=0.21/5=0.2；
    
- 没有命中：0。
    

多个 query 取平均。

比如：

- Query1 第一个相关在第 2 位：0.5；
    
- Query2 第一个相关在第 1 位：1.0；
    
- Query3 没有相关：0。
    

MRR=(0.5+1.0+0)/3=0.5MRR=(0.5+1.0+0)/3=0.5

**在 RAG 中**  
MRR 适合评估**只有一个最关键证据**，或者用户只关心“第一个正确结果”的场景。比如 FAQ、实体问答、单跳事实问答。

**注意**  
MRR 只看第一个相关结果，后面的相关文档完全不管。如果一个问题需要多个证据，MRR 不够。

---

### 4.3 nDCG：归一化折损累计增益

**定义**  
nDCG 考虑两件事：

1. **位置越靠前，权重越高**；
    
2. **相关性可以分级**，不只是相关/不相关。
    

先算 DCG，再除以理想排序的 DCG，得到 nDCG。

**公式**

常用形式：

DCG@k=∑i=1k2reli−1log⁡2(i+1)DCG@k=i=1∑k​log2​(i+1)2reli​−1​

其中：

- ii：排名位置；
    
- relireli​：第 i 个结果的相关性等级，比如 0、1、2、3；
    
- 分母 log⁡2(i+1)log2​(i+1) 是位置折损，越靠后贡献越小。
    

理想排序下算出的 DCG 叫 IDCG@k。

nDCG@k=DCG@kIDCG@knDCG@k=IDCG@kDCG@k​

nDCG 范围通常在 0 到 1，越大越好。

**直觉**  
假设相关性等级：

- 3 = 完全回答；
    
- 2 = 高度相关；
    
- 1 = 部分相关；
    
- 0 = 不相关。
    

一个高度相关文档排第 1，比排第 5 价值大得多。nDCG 会奖励“把最相关的东西排前面”。

**在 RAG 中**  
nDCG 常用于评估：

- Rerank 模型好不好；
    
- 混合检索融合后排序好不好；
    
- 多级相关性标注场景。
    

常见看 `nDCG@5`、`nDCG@10`，因为最终送给 LLM 的上下文通常只有 top 5～10。

**注意**  
nDCG 需要相关性标注。可以是二值，也可以多级。多级标注更贴近真实 RAG，因为不同 chunk 对答案的贡献不同。

---

### 4.4 三者对比

|指标|关注点|是否考虑位置|是否考虑多相关文档|是否支持多级相关性|典型场景|
|---|---|---|---|---|---|
|Recall@k|找全没|否，只看前 k|是|否，通常二值|召回阶段|
|MRR|第一个相关多靠前|是，但只看第一个|否|否|单答案问答、FAQ|
|nDCG@k|整体排序质量|是|是|是|重排、排序评估|

一句话总结：

- **Recall@k**：相关文档有没有进前 k；
    
- **MRR**：第一个相关文档排第几；
    
- **nDCG**：相关文档排得合不合理，越相关越靠前越好。
    

---

### 4.5 在 RAG 里怎么用

一个典型 RAG 检索评估流程：

text

召回阶段：
  看 Recall@50 / Recall@100
  目标：别漏掉关键证据
融合/重排阶段：
  看 MRR@10 / nDCG@10
  目标：把最相关证据排到前面
生成阶段：
  看答案正确率、忠实度、引用准确率
  目标：LLM 是否真的用对了证据

如果指标表现是：

- **Recall 高，nDCG 低**：证据都找到了，但排序差，rerank 需要优化；
    
- **nDCG 高，Recall 低**：前排很准，但漏了其他必要证据，召回需要优化；
    
- **MRR 高，nDCG 低**：第一个相关结果很靠前，但后面排序乱，或者多证据覆盖不好。
    

所以评估 RAG 检索不能只看一个指标，通常要 **Recall@k + nDCG@k + MRR** 结合看，再配合最终答案正确率和引用准确率。

## 5. GraphRAG：用途与用法

GraphRAG 的核心价值在于解决传统 RAG **“信息碎片化”** 和 **“缺乏全局视角”** 的根本问题。传统 RAG 像在图书馆里按关键词翻书，找到的是孤立片段；GraphRAG 是**先画一张人物关系网，再顺着网找线索**，让 AI 能够理解实体之间的复杂关联并进行推理。

---

### 5.1 GraphRAG 有什么用？

主要针对以下传统 RAG 难以处理的场景：

- **缺乏全局视角**：  
    提问“公司各部门的协作关系是怎样的？”，传统 RAG 只能返回几个相关片段，GraphRAG 能给出完整的关系网络图。
    
- **无法理解指代关系**：  
    文档中“他们共同管理公司”的“他们”，传统 RAG 无法关联到前文提到的“张三”和“李四”，GraphRAG 可以通过实体链接解决。
    
- **多跳推理困难**：  
    对于“张三的团队成员中，谁参与过 AI 项目？”这类需要多步推理的问题，GraphRAG 可以沿着“张三 → 管理谁 → 这些人 → 负责什么项目”的路径进行链式推理。
    
- **信息碎片化**：  
    检索结果像拼图碎片，缺乏整体关联，GraphRAG 通过社区摘要和层次化结构，提供更完整的上下文。
    

**实测数据参考**：  
在多跳推理任务（如 HotpotQA）中，GraphRAG 的 F1 分数（61.66）优于传统 RAG（60.04）；但在单跳事实问答中，传统 RAG 反而领先（64.78 vs 63.01）。

---

### 5.2 GraphRAG 怎么用？—— 两阶段工作流程

GraphRAG 的工作流程分为**索引阶段（离线构建）** 和**查询阶段（在线检索）**。

#### 索引阶段：构建知识图谱

目标：将非结构化文档转化为结构化知识网络。

1. **文本分块**：将原始文档切分为较小的文本块（Chunks）。
    
2. **实体与关系抽取**：利用 LLM 从每个文本块中识别关键**实体**（人物、公司、产品）和它们之间的**关系**（管理、投资、合作）。  
    例如，从“黄果树瀑布是中国著名景点”中提取实体“黄果树瀑布”和属性“著名景点”。
    
3. **图谱构建**：将抽取的实体和关系存储到图数据库中，形成知识图谱。
    
4. **社区检测与摘要**：使用图算法（如 **Leiden 算法**）将图谱中的节点聚类成不同“社区”，并为每个社区生成摘要。这一步是 GraphRAG 支持**全局性问题**回答的关键。
    

#### 查询阶段：基于图谱的检索

当用户提问时，GraphRAG 不再仅仅是做向量相似度匹配。

- **全局查询（Global Search）**：  
    利用索引阶段生成的**社区摘要**，对整个知识库进行推理和总结。  
    **适合**：“这份数据集的主要主题是什么？”这类宏观分析问题。
    
- **局部查询（Local Search）**：  
    从用户问题中识别实体，然后**沿着图谱中的关系**进行遍历和扩展，找到与该实体相关的所有上下文信息。  
    **适合**：“张三的团队成员有哪些？”这类针对特定实体的深入分析。
    

---

### 5.3 如何实现与上手？

- **官方方案（微软 GraphRAG）**：  
    可以通过 `pip install graphrag` 安装。基本流程是：初始化项目、在 `input` 目录放入文档、配置 LLM 的 API Key 和模型、运行索引构建命令，最后执行查询命令。
    
- **使用 Neo4j 集成**：  
    Neo4j 提供了官方的 GraphRAG 包，可以方便地与图数据库集成，实现基于向量和图的混合检索。核心组件包括嵌入器（Embedder）、大语言模型（LLM）和检索器（Retriever）。
    

---

### 5.4 何时使用 GraphRAG？—— 选型决策

GraphRAG 并非万能，它更适合作为 RAG 系统中的一路召回，用来解决特定类型的问题。

|场景|推荐方案|原因|
|---|---|---|
|**多跳推理**（如：谁向批准此预算的人汇报？）|**GraphRAG**|需要跨越多个文档追踪实体关系链|
|**全局摘要**（如：这份合同集的主要风险点？）|**GraphRAG**|需要理解整个数据集的宏观主题和社区结构|
|**实体密集文档**（如：法律、技术文档）|**GraphRAG**|实体关系越密集，图谱的价值越大|
|**简单事实问答**（如：公司 CEO 是谁？）|**传统 RAG**|答案通常在单一文档块中，向量检索足够且成本更低|
|**快速原型 / MVP**|**传统 RAG**|GraphRAG 的索引构建成本高、周期长|

GraphRAG 的索引成本（LLM 调用、图数据库）远高于传统 RAG，在决定使用前需要评估其对**复杂关系推理**和**全局洞察**的需求是否足以覆盖这部分成本。

## 6. 总结与选型建议

### 6.1 核心结论

- 向量检索只是召回的一路，解决“语义相似”，不解决“精确证据”和“关系推理”。
    
- BM25 / 稀疏检索补精确匹配，适合专名、ID、代码、数字、法律条款。
    
- 混合检索是通用 RAG 最稳默认方案：**dense + BM25 + RRF + rerank**。
    
- RRF 按排名融合，简单鲁棒，适合多路召回。
    
- Rerank 是精排，不能替代召回，只能优化已召回集合。
    
- 查询改写提升召回，但要注意 query drift，通常保留原 query 一起检索。
    
- 评估检索质量要组合看 **Recall@k、MRR、nDCG@k**，再结合答案正确率和引用准确率。
    
- GraphRAG 适合多跳推理、全局摘要、实体密集文档；简单事实问答和快速原型优先传统 RAG。
    

### 6.2 推荐默认架构

text

Query
  -> 查询改写 / 路由 / 过滤抽取
  -> 并行召回：向量 top50 + BM25 top50
  -> RRF 融合
  -> 去重 / 多样性
  -> Cross-Encoder Rerank top20 -> top5
  -> 上下文组装
  -> LLM 生成 + 引用

### 6.3 按场景选型

|场景|推荐检索方案|
|---|---|
|通用文本 RAG|dense + BM25 + RRF + rerank|
|代码、日志、法律、医疗|提高 BM25 / 精确匹配权重|
|多跳、综述、关系推理|查询分解 + GraphRAG + 迭代检索|
|表格、指标、数据库|Text2SQL + 向量混合|
|多语言|多语言 embedding + BM25 / 稀疏检索|
|快速原型|向量检索 + 简单 rerank，先验证效果|

---

> 最终一句话：RAG 检索的核心不是“用哪个检索”，而是“多路召回 + 融合 + 重排 + 查询改写 + 评估闭环”的系统工程。
