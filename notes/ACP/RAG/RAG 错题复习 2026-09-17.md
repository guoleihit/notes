## 一、GraphRAG 技术

### 1. GraphRAG 结合了哪两种技术？

**答案：检索增强生成（RAG）+ 查询聚焦摘要（QFS）**

- **RAG**：从外部知识库检索相关信息，交给大模型生成答案。
    
- **QFS**：针对某个查询，对大量文本进行聚焦式摘要与归纳。
    
- **GraphRAG 的核心**：通过构建**知识图谱**组织实体、关系和社区摘要，在需要**全局理解**或**多跳推理**的问题上，表现优于传统 RAG。

## 二、RAG 评估指标

### 2. 四大核心指标对比

|指标|关注点|典型问题|对应选项|
|---|---|---|---|
|**Context Precision（上下文精确率）**|相关召回文本段**排名是否靠前**|相关段落被排在末尾|B|
|**Answer Relevancy（答案相关性）**|答案是否**切题**|问“如何退款”，答“退货政策历史”|D|
|**Faithfulness / Groundedness（忠实度/接地性）**|答案是否**忠于召回原文**|答案包含检索文本中不存在的信息（幻觉）|C|
|**整体回答质量**|综合多维度|全面评估|A|

### 3. 各指标如何评判？

**A. 整体回答质量** —— 由一组指标综合衡量：

- **忠实度 / 接地性**：答案是否严格基于检索上下文，有无编造。
    
- **答案正确性**：与标准参考答案比对事实内容。
    
- **答案完整性**：是否充分覆盖问题的各个要点。
    

评判逻辑：先看**是否忠于原文** → 再看**事实对不对** → 最后看**要点全不全**。

**B. Context Precision（上下文精确率）**：

- 衡量检索结果中，**真正相关的文本段是否被排在更靠前的位置**。
    
- 相关文本排前面 → 分数高；被不相关文本挤到后面 → 分数低。
    
- 本质是**排序质量**指标，不是回答质量指标。
    

**C. 答案忠实度 / 接地性**：

- 检查生成答案中的**每一句话**，是否能从召回文本段中找到依据。
    
- 通常由 LLM 执行：把答案分解为独立事实陈述，逐一在上下文中验证。
    
- 高分 = 完全基于给定材料；低分 = 出现**幻觉**。
    

**D. 答案相关性**：

- 关注答案是否**直接、切题**地回答了用户问题，不关心是否忠于原文。
    
- **反向生成问题法**（RAGAS 常用）：根据答案反向生成问题 → 计算与原始问题的语义相似度。
    
- **直接打分法**：让 LLM 阅读“问题 + 答案”，按 1–5 分或 0–1 分打分。
    

### 4. 典型反例

- **提问**：GraphRAG 结合了哪两种技术？
    
- **检索文本**：正确提到了 RAG 和 QFS
    
- **生成答案**：“GraphRAG 是一种基于知识图谱的检索方法，广泛应用于企业搜索。”
    

|指标|表现|
|---|---|
|忠实度（C）|高分（忠于原文）|
|Context Precision（B）|高分（相关文本排名靠前）|
|答案相关性（D）|**低分**（没有回答问题）|

> 结论：D 评判的是答案的**切题程度**，独立于忠实度和检索质量之外。

## 三、HyDE：用假设文档增强检索

### 5. 什么是“用假设文档来增强检索”？

指 **HyDE（Hypothetical Document Embeddings，假设文档嵌入）**。

**核心思路**：先让大模型“编”一个答案，再用这个编出来的答案去检索真实文档。

### 6. 为什么需要 HyDE？

传统 RAG 的检索缺陷：

- **用户提问**通常很短。
    
- **知识库文档**通常很长、很正式。
    
- 两者在**向量空间里的距离可能很远**，导致匹配不上。
    
- 根本原因：**问题和答案的表述方式往往不一致**。
    

### 7. HyDE 的流程

1. **生成假设文档**：用 LLM 根据问题生成一个“假设答案文档”（可能包含事实错误，但用词、风格、结构接近真实文档）。
    
2. **编码假设文档**：把假设文档转成向量，而非用原始问题转向量。
    
3. **检索**：用假设文档的向量在知识库中找最相似的真实文档。
    
4. **生成**：把检索到的真实文档交给 LLM，生成最终答案。
    

### 8. 关键点

- 假设文档**不需要正确**，作用是**搭一座语义桥梁**。
    
- 主要解决**查询与文档表述不一致**导致的召回问题。
    
- 代价：多一次 LLM 调用，增加延迟和成本。

## 四、切片向量化与存储阶段

### 9. 准备测试数据用哪个方法？

**答案：A. compare_embeddings 函数**

- 该阶段核心任务：文档切分 → 转向量 → 存入向量库。
    
- `compare_embeddings` 用于：接收几段文本，分别计算 embedding，输出相似度对比，**检查切片和向量化是否符合预期**。
    
- 其他选项（增加训练数据、减少推理时间、增加参数数量）均不属于准备测试数据。

## 五、答疑机器人优化

### 10. 为什么优化后的答疑机器人不需要每次提问都走 RAG 链路？

**答案：A. 节省资源并避免知识库信息干扰大模型推理**

- 优化后加入**路由 / 意图判断机制**：
    
    - **简单问题**（寒暄、常识、固定话术）→ 直接由大模型回答。
        
    - **需要知识库支撑的问题** → 才走 RAG 链路。
        
- 好处：
    
    1. **节省资源**：避免每次向量检索、重排、拼接上下文，降低延迟和成本。
        
    2. **避免知识库信息干扰**：不需要外部知识的问题强行检索，可能引入不相关片段，干扰推理。

## 六、知识库上传限制

### 11. 本地上传知识库数据时，最大支持单文档大小为？

**答案：C. 100MB**

> 注意：该限制**没有统一标准**，取决于具体平台。

|平台|单文档大小限制（默认）|备注|
|---|---|---|
|腾讯云 TCDataAgent|**100MB**|PDF/Word/PPT；MD/TXT 仅 10MB，图片 20MB|
|华为云盘古|128MB|超过 60MB 建议用 API 上传|
|RAGFlow|128MB|Web UI 曾有 8-10MB 临时 Bug，现已移除|
|Dify|15MB|可通过 `UPLOAD_FILE_SIZE_LIMIT` 调整|
|阿里云百炼|150MB|PDF/Word；TXT/Markdown 仅 10MB|
|腾讯云（另一产品）|200MB|表格类文件为 20MB|

**实际使用时**：查看具体平台官方文档，或检查环境变量配置（如 `MAX_CONTENT_LENGTH`、`UPLOAD_FILE_SIZE_LIMIT`）。

## 七、多查询召回技术

### 12. 哪个技术通过提出多个相关查询来提高问题理解的广度和深度？

**答案：B. Multi-Query 多路召回**

- **做法**：让大模型针对原始问题，自动生成多个语义相关但表述不同的查询，分别检索后合并结果。
    
- **目的**：提高问题理解的**广度和深度**，从不同角度召回更全面的信息。
    

### 13. 易混淆技术对比

|技术|核心做法|侧重点|
|---|---|---|
|**Multi-Query 多路召回**|生成多个相关查询，分别检索后合并|提高理解广度与深度|
|**Step Back 问题摘要**|把具体问题抽象成更上位的概念或原理|抽象与推理|
|**Decomposition 问题分解**|把复杂问题拆成若干子问题，分别检索后综合|化繁为简，解决多跳问题|
|**RAG-Fusion 问题过滤融合**|对多路召回结果做融合排序（如 RRF）|与 Multi-Query 配合使用|

> 注意：RAG-Fusion 与 Multi-Query 关系密切，通常结合使用。但“**提出多个相关查询**”这个动作本身，对应的是 **Multi-Query**。
