## 复习建议 ①：三个层面 + 两套命名

### 1. 生成相关「三个层面」——最容易混

| 层面 | 是什么 | 关键词 | 举例 |
|---|---|---|---|
| **生成范式** | 整体怎么一步步生成 | 自回归 | 用前文预测下一个 Token |
| **模型结构 / 内部机制** | 每一步如何算上下文 | 自注意力 | Q / K / V 加权求和 |
| **解码策略** | 拿到概率后怎么选词 | 采样 / 贪心 | temperature、top-k、top-p、beam search |

> **记忆口诀**：**范式（自回归）→ 机制（自注意力）→ 策略（采样）**，从大到小，别串层。
> **易错**：「自注意力采用自回归方式」❌ —— 一个是结构，一个是范式。

### 2. API 操作名 vs SDK 方法名

| HTTP 操作（文档标题） | Python SDK 方法 | 作用 |
|---|---|---|
| Create message | `client.beta.threads.messages.create` | 创建消息 |
| Retrieve message | `client.beta.threads.messages.retrieve` | 取单条消息 |
| Modify message | `client.beta.threads.messages.update` | 改消息（**只能改 metadata**） |
| List messages | `client.beta.threads.messages.list` | 列出消息 |
| Create run | `client.beta.threads.runs.create` | 启动一次运行 |
| Submit tool outputs | `client.beta.threads.runs.submit_tool_outputs` | 回传工具结果 |

> **易错**：`modify` 是 **HTTP 操作名**，不是 SDK 独立函数；SDK 里叫 `update`。
> **口径更新**：Assistants API 已弃用，实际开发迁移到 Responses API（无独立 Message 资源，上下文走 `input`）。

### 3. 自测

- [ ] 「根据已生成文本预测下一个词」叫什么？—— **自回归**
- [ ] 「让每个词关注上下文中其他词」属于哪一层？—— **内部机制（自注意力）**
- [ ] 「temperature / top-p」属于哪一层？—— **解码策略**
- [ ] Python SDK 改消息用 `modify` 还是 `update`？—— **`update`**

## 复习建议 ②：长度限制 / 格式约束

### 1. 答题口径（关键）

| 题型 | 怎么答 |
|---|---|
| **单选题**（如「如何修改摘要函数使其不超过 80 字」） | 选 **提示词约束**（A） |
| **工程题 / 多选题** | 答 **组合方案**：提示词 + 解码参数 + 后处理校验重试 + 兜底截断 |
| **陷阱** | 生成后 `query[:80]`、截断输入 `document[:80]` 都是错的 |

> **为什么单选选 A**：A 是唯一「通过约束模型输出」的合理方向；B/C 破坏语义或输入。
> **为什么工程不能只靠 A**：提示词是**软约束**，模型不保证精确计数。

### 2. 四个常见约束及其边界

| 手段 | 管什么 | 局限 |
|---|---|---|
| 提示词「不超过 80 字」 | 意图约束 | 软约束，可能超 |
| `max_tokens` / `max_completion_tokens` | **Token** 数上限 | Token ≠ 汉字；可能句中断 |
| `stop` | 在指定串处停 | 只能保证截断点，不保证长度 |
| 后处理 `text[:80]` | 字符数 | 破坏语义、标点、词语 |

### 3. 代码模板：分层防御

```python
import re

def _char_len(s: str) -> int:
    return len(re.sub(r"\s", "", s))

def truncate_at_punct(text: str, limit: int) -> str:
    text = text[:limit]
    for i in range(len(text) - 1, -1, -1):
        if text[i] in "。！？；，,.!?;":
            return text[:i + 1]
    return text

def summarize(llm, doc: str, limit: int = 80) -> str:
    prompt = f"请用不超过 {limit} 个汉字总结。超限时优先删减细节，保留结论。"
    text = llm(prompt, doc, max_tokens=limit * 2)   # ① 物理上限
    for _ in range(3):                               # ② 校验 + 重试
        if _char_len(text) <= limit:
            return text
        text = llm(f"把下面内容压缩到 {limit} 个汉字以内：\n{text}",
                   max_tokens=limit * 2)
    return truncate_at_punct(text, limit)            # ③ 兜底语义截断
```

### 4. 自测

- [ ] `max_tokens=80` 能保证输出 80 个汉字吗？—— **不能，它限制的是 Token**
- [ ] 提示词写「不超过 80 字」一定能成功吗？—— **不能，软约束**
- [ ] 生成后用 `query[:80]` 有什么问题？—— **可能截断词/标点，破坏语义**

## 复习建议 ③：Run 生命周期与 requires_action

### 1. 状态机

```
queued → in_progress ──► completed
              │  ▲
              ▼  │ submit_tool_outputs
        requires_action
              │
              └──► failed / cancelled
```

| 状态 | 含义 | 客户端动作 |
|---|---|---|
| `queued` | 排队 | 继续轮询 |
| `in_progress` | 生成中 | 继续轮询 |
| `requires_action` | 需要工具结果 | **本地执行函数 → 提交 `tool_outputs`** |
| `completed` | 完成 | 取消息 |
| `failed` | 失败 | 读 error |
| `cancelled` | 取消 | —— |

> **口诀**：看到 `requires_action` 就等于「模型说：我调用了函数，请你把结果给我」。

### 2. Function Calling 闭环代码（Assistants API）

```python
import json, time
from openai import OpenAI

client = OpenAI()

def execute_tool(name: str, args: dict) -> str:
    if name == "get_weather":
        return json.dumps({"city": args["city"], "temp": 26})
    raise ValueError(f"unknown tool: {name}")

def forward_and_submit_outputs(run, thread_id: str):
    """执行模型要求的工具，并把结果提交回服务器，推动 Run 继续。"""
    outputs = []
    for tc in run.required_action.submit_tool_outputs.tool_calls:
        args = json.loads(tc.function.arguments or "{}")
        result = execute_tool(tc.function.name, args)
        outputs.append({"tool_call_id": tc.id, "output": result})
    return client.beta.threads.runs.submit_tool_outputs(
        thread_id=thread_id, run_id=run.id, tool_outputs=outputs
    )

def run_to_completion(thread_id: str, assistant_id: str):
    run = client.beta.threads.runs.create(
        thread_id=thread_id, assistant_id=assistant_id)
    while run.status in ("queued", "in_progress", "requires_action"):
        run = client.beta.threads.runs.retrieve(
            thread_id=thread_id, run_id=run.id)
        if run.status == "requires_action":
            run = forward_and_submit_outputs(run, thread_id)
        else:
            time.sleep(1)
    return run
```

> **记忆**：`forward_and_submit_outputs` = **执行 function call + 提交 tool_outputs**。
> 不是创建 Assistant（`Assistants.create`）、不是提 query（`Messages.create`）、不是取回复（`Messages.list`）。

## 复习建议 ④：延迟优化

### 1. 优先方向（按性价比）

| 优先级 | 手段 | 为什么有效 |
|---|---|---|
| 高 | **上下文缓存 / Prompt Caching** | 复用已算好的 KV，降低首 Token 延迟 |
| 高 | **提前生成 / 预计算 / 响应缓存** | 重复或可预测的内容直接复用 |
| 高 | **减少输入 Token** | 输入短 → 处理快 |
| 高 | **流式输出** | 不减少总时长，但让用户先看到首字 |
| 中 | **选更小/更快的模型** | 延迟更低 |
| 中 | **并行化 / 预取** | 提高吞吐、隐藏等待 |
| ❌ | **盲目用更大模型** | 参数越大通常越慢 |

> **易错**：把「增大模型」当成降延迟手段——方向反了。

### 2. 流式 + 缓存的常见写法

```python
# 流式：让用户尽快看到第一个字
stream = client.chat.completions.create(
    model="gpt-4o-mini",
    messages=[{"role": "user", "content": "写一段产品介绍"}],
    stream=True,
)
for chunk in stream:
    delta = chunk.choices[0].delta.content
    if delta:
        print(delta, end="", flush=True)

# 缓存友好：固定内容（system、背景）放前面，变化内容放后面
messages = [
    {"role": "system", "content": "你是一个客服助手。"},   # 固定前缀
    {"role": "user", "content": user_question},            # 变化部分
]
```

### 3. 自测

- [ ] 哪种方法**不**助于降低等待时间？—— **用参数量更大的模型**
- [ ] 流式输出会减少总生成时间吗？—— **不会，但改善感知等待**
- [ ] 缓存友好的消息顺序？—— **固定内容在前，变化内容在后**

## 一页速记卡

```
生成三层：范式(自回归) → 机制(自注意力) → 策略(采样)
命名两套：HTTP = modify   SDK = update（只改 metadata）
Message 方法：create / retrieve / update / list
Run 状态：queued → in_progress → requires_action → completed
工具闭环：requires_action → 本地执行 → submit_tool_outputs → 继续
长度控制：提示词(软) + max_tokens(Token数) + 校验重试 + 兜底截断
降延迟：缓存 / 预计算 / 减少输入 / 流式 / 小模型（≠增大模型）
长文档：分段扫描 + 多类型识别 + 汇总
```
