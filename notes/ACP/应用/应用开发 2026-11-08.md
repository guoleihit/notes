## 二、逐题解析

### 题目5：Assistant API 中 `Message` 类包含哪些函数？

**题目：** Assistant API 中 `Message` 类包含了各类关于消息的函数，以下哪些选项属于 `Message` 类中的函数？

A. `retrieve`  
B. `create`  
C. `update`  
D. `modify`  
E. `search`  
F. `list`

**答案：A、B、C、F**

**解析：**

- `retrieve`：检索单条消息。
    
- `create`：创建消息。
    
- `update`：更新/修改消息。
    
- `list`：列出线程中的消息。
    
- `modify`：在 REST API 层面对应 “Modify message” 操作，但 Python SDK 的 `Message` 类中对应方法是 `update`，不是独立的 `modify` 方法。
    
- `search`：不属于 `Message` 类的标准函数。
    

**知识点总结：**

- Assistant API 的 `Message` 类核心方法：`create`、`retrieve`、`update`、`list`。
    
- 注意区分 **HTTP API 操作名** 与 **SDK 方法名**。
    

**扩展：**

- 官方 API 参考中“Modify message”示例的 Python 代码通常调用 `client.beta.threads.messages.update(...)`。
    
- 答题时若严格问“SDK 类中的函数”，不应把 `modify` 当作独立函数；若问“HTTP 操作”，则 `modify` 是修改消息的端点名称。

### 题目8-1：以下哪些方法有助于减少大模型应用的输出结果等待时间？

**题目：** 以下哪些方法有助于你减少大模型应用的输出结果等待时间？

A. 使用参数量更大的模型  
B. 使用支持上下文缓存的模型API  
C. 提前生成和复用内容  
D. 减少输入Token数量

**答案：B、C、D**

**解析：**

- A：参数量更大的模型通常推理延迟更高，不利于减少等待时间。
    
- B：上下文缓存可复用已处理的上下文，减少重复计算，降低首 Token 延迟。
    
- C：提前生成和复用内容可减少实时生成耗时。
    
- D：减少输入 Token 数量可缩短输入处理时间，有助于降低延迟。
    

**知识点总结：**

- 降低大模型应用延迟的常见方向：缓存、预计算、减少输入长度、流式输出、模型选择、并行化等。
    

**扩展：**  
“提前生成和复用内容”的落地方式包括：

1. **KV Cache / Prompt Caching**：复用长上下文的预计算缓存。
    
2. **响应缓存**：对重复或语义相似查询直接返回缓存答案。
    
3. **Predicted Outputs**：对大部分已知、只需微调的内容，让模型只生成差异部分。
    
4. **工具 Schema 缓存**：Agent 工具定义静态，可持久化复用。
    
5. **RAG 检索预取**：在对话间歇期提前检索并缓存可能用到的内容。

### 题目6：大语言模型生成文本时预测下一个词的方式称为什么？

**题目：** 大语言模型在生成文本时，依赖于一种特定的方式来预测下一个词的概率。这种方式允许模型根据已经生成的文本预测接下来的词语。这种方式被称为什么？

A. 自注意力机制  
B. 自回归  
C. 条件概率预测  
D. 概率分布采样

**答案：B. 自回归**

**解析：**

- 大语言模型通常以**自回归**方式生成文本：根据已生成序列 x1,…,xtx1​,…,xt​，预测下一个 Token xt+1xt+1​ 的概率：
    
    P(xt+1∣x1,…,xt)P(xt+1​∣x1​,…,xt​)
- **自注意力机制**是模型内部结构，用于计算上下文表示。
    
- **条件概率预测**是对预测过程的数学描述。
    
- **概率分布采样**是解码策略之一。
    

**知识点总结：**

- 自回归是生成范式；自注意力是内部计算机制；采样是解码策略。三者层面不同。
    

**扩展：**  
更严谨表述：**模型以自回归方式逐步生成 Token；每一步利用自注意力等组件，根据已生成上下文计算下一个 Token 的概率分布，再通过采样或选择策略得到下一个 Token。** 不宜说“自注意力机制采用自回归方式”，因为一个是结构机制，一个是生成范式。

### 题目8-2：检测文档中营销表达时哪种方法更全面？

**题目：** 在通过大语言模型检测文档内容中是否存在营销表达时，下列哪种方法可以更全面地识别问题？

A. 一次性生成所有类型的识别结果  
B. 按照营销表达分类逐条单独识别营销词汇  
C. 仅识别有内容错误的部分  
D. 按文档段落扫描整篇文档，每段完成所有类型的识别，汇总后一次性返回结果

**答案：D**

**解析：**

- A：一次性处理所有类型，输入长、任务多，容易遗漏。
    
- B：偏重词汇匹配，忽略上下文和隐性营销表达。
    
- C：目标不一致，只关注内容错误，不覆盖营销表达。
    
- D：按段落扫描覆盖全文，每段完成多类型识别，能结合上下文并汇总，覆盖更全面。
    

**知识点总结：**

- 长文档检测宜采用“分段扫描 + 多类型识别 + 汇总”的策略。
    
- 结合上下文可减少漏判和误判。
    

**扩展：**  
工程上还可结合：分段重叠窗口、每段输出结构化结果、最后去重汇总、对边界段落二次校验。

### 摘要题：修改生成摘要函数使摘要不超过80个字

**题目：** 在调用大语言模型对话的API过程中，如果要修改生成摘要的函数，使其生成的摘要不超过80个字，应该如何修改？

A. 在提示词部分明确写出摘要本身的内容不超过80个字  
B. 假设生成结果为 `query`，生成结果后添加 `query = query[:80]`  
C. 假设输入的文档为 `document`，在函数开头添加 `document = document[:80]`  
D. 以上修改方法均不正确

**答案：A（单选题中最合理）**

**解析：**

- A：通过提示词约束模型输出长度，是四个选项中最符合“修改生成摘要函数”的做法。
    
- B：生成后截断可能破坏语义、标点和词语，且“80个字”与字符截取不等价。
    
- C：截断输入文档会导致摘要基于不完整内容生成，错误。
    
- D：不成立，因为 A 是合理方向。
    

**重要补充：A 有概率失败。** 提示词约束是“软约束”，模型不保证严格满足“80个字”的精确计数要求。

**知识点总结：**

- 提示词约束是软约束；`max_tokens` 控制 Token 数而非汉字数；硬截断保长度但不保语义完整。
    
- 工程上应组合使用：提示词优化 + 解码参数 + 后处理校验 + 条件重试 + 兜底截断。
    

**扩展：最正确的工程方案是分层防御**

1. **提示词优化**：明确“不超过80个汉字”，说明超限时优先删减细节，并提供长度符合要求的 Few-Shot 示例。
    
2. **解码参数控制**：设置 `max_tokens` / `max_completion_tokens` 作为物理上限；可用 `stop` 在句号、问号等语义边界停止。
    
3. **后处理校验 + 条件重试**：统计实际字数；若超长，将原输出和更严格指令一起让模型压缩，最多重试2–3次。
    
4. **兜底语义截断**：仍超长时，在80字范围内从后向前寻找最近标点截断，作为最后安全网。
    

结论：**单选选 A；工程上不能只依赖 A，需“提示词 + 参数 + 校验重试 + 兜底截断”组合。**

### 题目26：`forward_and_submit_outputs` 函数的核心功能

**题目：** 下列AssistantAPI示例代码中 `forward_and_submit_outputs` 函数的核心功能是什么？

A. 创建新的Assistant  
B. 向Assistant提交用户query  
C. 执行function call并将结果提交给服务器  
D. 获取Assistant的回复

**答案：C. 执行function call并将结果提交给服务器**

**解析：**

- 该函数通常在 `Run` 状态变为 `requires_action`，且 `required_action.type` 为 `submit_tool_outputs` 时触发。
    
- 它根据模型要求的函数名和参数，在本地执行实际工具函数，然后通过 `submit_tool_outputs` 将结果提交回服务器，使 Run 继续。
    
- A 由 `Assistants.create` 完成；B 由 `Messages.create` 完成；D 由 `Messages.list` 等完成。
    

**知识点总结：**

- Assistant API 的 Function Calling 流程：模型返回 `requires_action` → 本地执行工具 → 提交 `tool_outputs` → Run 继续。
    
- `forward_and_submit_outputs` 负责“执行工具并回传结果”。
    

**扩展：**  
常见 Run 状态包括 `queued`、`in_progress`、`requires_action`、`completed`、`failed`、`cancelled` 等。处理 `requires_action` 是工具调用闭环的关键。

## 三、知识点总结

1. **Assistant API `Message` 类**：核心方法为 `create`、`retrieve`、`update`、`list`；`modify` 是 HTTP 操作名，Python SDK 中对应 `update`。
    
2. **降低大模型等待时间**：上下文缓存、提前生成与复用、减少输入 Token、流式输出、合理选择模型等。
    
3. **自回归生成**：根据已生成文本逐步预测下一个 Token；自注意力是内部机制，采样是解码策略。
    
4. **长文档营销表达检测**：分段扫描、每段多类型识别、汇总返回，比一次性生成或逐条词汇识别更全面。
    
5. **摘要长度控制**：提示词是软约束，工程上需结合参数限制、后处理校验、条件重试和兜底截断。
    
6. **Function Calling 闭环**：`forward_and_submit_outputs` 执行本地函数并将结果提交服务器，推动 Run 继续。

## 四、易错点汇总

|易错点|正确理解|
|---|---|
|把 `modify` 当作 Python SDK `Message` 类独立函数|SDK 中修改消息的方法是 `update`；`modify` 是 HTTP 操作名|
|认为参数量更大的模型能减少等待时间|通常会增加延迟，不利于减少等待|
|混淆自回归、自注意力、采样|自回归是生成范式；自注意力是内部机制；采样是解码策略|
|营销检测只做词汇匹配|应结合段落上下文和多类型识别，覆盖隐性表达|
|认为提示词写“不超过80字”一定成功|软约束有失败概率，需后处理校验和重试|
|混淆 `forward_and_submit_outputs` 与创建消息/获取回复|它负责执行 function call 并提交 tool outputs|

## 五、复习建议

- 重点区分 **API 操作名 vs SDK 方法名**、**生成范式 vs 模型结构 vs 解码策略**。
    
- 涉及“长度限制”“格式约束”的题目，单选选提示词约束，但工程题要答组合方案。
    
- Assistant API 题目要熟悉 Run 的生命周期和 `requires_action` 的处理逻辑。
    
- 延迟优化题目优先考虑缓存、预计算、减少输入和流式输出，而不是盲目增大模型。
